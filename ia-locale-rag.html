Faire tourner des LLM en local
et interroger ses propres documents

Confidentialité, coût, latence, souveraineté : un guide concret pour devs et chefs de projet qui évaluent l'exécution de modèles on-premise plutôt que via une API cloud — avec les chiffres VRAM/RAM qui comptent et le RAG 100 % local.

1Pourquoi (et quand) faire de l'IA en local

Le cloud (OpenAI, Anthropic, etc.) reste imbattable sur la qualité brute et la simplicité. Le local devient pertinent dès que la donnée, le coût récurrent ou l'indépendance pèsent plus lourd que les quelques points de qualité gagnés par les plus gros modèles propriétaires.

Cas d'usage qui justifient le local

🔒 Données sensibles & code propriétaire

Aucune donnée ne quitte le réseau. Indispensable pour du code source confidentiel, des dossiers médicaux/juridiques, des documents RH ou financiers. Pas de risque que vos prompts servent à un entraînement tiers.

⚖️ Conformité RGPD & souveraineté

Pas de transfert hors UE, pas de sous-traitant à auditer, traçabilité totale. Simplifie radicalement les analyses d'impact (PIA) et les exigences de certains secteurs régulés (santé, défense, banque, secteur public).

💸 Coût récurrent maîtrisé

Au-delà d'un certain volume, le coût par token du cloud devient une rente. En local, le coût est un investissement matériel amorti : une station bien dimensionnée se rentabilise face à des milliers d'appels/jour (agents, traitement batch, autocomplétion).

📡 Hors-ligne & faible latence

Fonctionne sans connexion (terrain, site industriel, air-gap). Latence locale stable, pas de rate-limit ni de coupure d'API côté fournisseur. Idéal pour de l'autocomplétion ou des boucles d'agent très bavardes.

Les limites — à dire honnêtement

  • Plafond de qualité. Un 70B local reste en dessous des meilleurs modèles cloud frontières sur le raisonnement complexe et les contextes très longs.
  • Coût matériel initial. Une vraie station à GPU 24–48 Go se chiffre en milliers d'euros.
  • Ops à votre charge. Mises à jour, monitoring, sécurité, mises à l'échelle : c'est vous l'équipe infra.
  • Débit limité. Une seule machine sert peu d'utilisateurs en parallèle sans dégradation.
  • Fenêtre de contexte. Souvent plus courte en pratique (la VRAM est mangée par le cache KV).
  • Écosystème mouvant. Modèles et outils évoluent vite ; il faut suivre.
Règle de décision rapide Donnée sensible + volume élevé + besoin offline → local. Qualité maximale + usage ponctuel + pas de contrainte de données → cloud. Beaucoup d'équipes finissent en hybride : local par défaut, cloud en débordement pour les tâches les plus dures.

2Les outils : Ollama vs LM Studio

Ce sont les deux portes d'entrée les plus simples. Les deux embarquent llama.cpp sous le capot et exposent une API compatible OpenAI en local — c'est le point clé pour intégrer dans un workflow dev existant.

Ollama — le « Docker des LLM »

CLI-first, pensé pour les devs et le scripting. ollama pull / ollama run, un Modelfile pour personnaliser, un serveur qui tourne en daemon. Parfait pour intégrer dans du code, des conteneurs, du CI.

  • Léger, scriptable, idéal serveur/headless
  • API OpenAI sur localhost:11434
  • Énorme écosystème d'intégrations (VS Code, Open WebUI…)
  • Pas de GUI native (sélection de modèle moins guidée)

LM Studio — le confort du GUI

Application bureau (Win/Mac/Linux) avec catalogue de modèles, chat intégré, réglages visuels (offload GPU, contexte) et un serveur local en un clic. Idéal pour découvrir, tester et comparer sans toucher au terminal.

  • Recherche/téléchargement de modèles guidé (Hugging Face)
  • Serveur API OpenAI sur localhost:1234
  • Visualise l'impact RAM/VRAM avant de charger
  • Moins naturel à automatiser/scripter côté serveur

Exposer l'API locale (compatible OpenAI)

Le gros intérêt : votre code existant qui parle à OpenAI fonctionne en changeant juste l'URL de base et la clé.

# Ollama
curl http://localhost:11434/v1/chat/completions -d '{
  "model": "qwen2.5-coder:7b",
  "messages": [{"role":"user","content":"Refactore cette fonction C#"}]
}'

# Côté client (Python/C#/JS) : base_url = http://localhost:11434/v1
# api_key = "ollama" (factice, non vérifiée)

Les autres alternatives, en bref

llama.cpp

Le moteur C/C++ bas niveau sous Ollama/LM Studio. Contrôle total, performances, mais à la main. Pour qui veut optimiser finement.

vLLM

Moteur d'inférence haut débit pour servir en prod (multi-utilisateurs, GPU). Plus complexe, orienté serveur GPU, pas laptop.

Jan

Alternative open-source type LM Studio, 100 % offline, interface soignée. Bon compromis GUI + ouverture.

GPT4All

Desktop grand public, simple, RAG local intégré. Léger, orienté CPU, pratique sur petites machines.

Open WebUI

Interface web (type ChatGPT) qui se branche sur Ollama. Multi-utilisateurs, RAG, gestion de docs. Excellent front d'équipe.

AnythingLLM

Solution RAG clé en main (desktop ou Docker) : ingestion docs, base vectorielle, espaces de travail. Voir section 5.

3Modèles, quantization & besoins machine

Trois variables déterminent ce qui tourne chez vous : la taille du modèle (paramètres), la quantization (précision des poids) et la mémoire (VRAM sur GPU, RAM sur CPU, mémoire unifiée sur Apple Silicon).

Taille du modèle (paramètres)

Plus de paramètres = plus « intelligent » mais plus gourmand et plus lent. Ordres de grandeur utiles :

1B–3BAutocomplétion, classification, tâches simples. Tourne partout, même CPU.
7B–14BLe sweet spot. Bon assistant code/texte, raisonnement correct. Cible des laptops/desktops sérieux.
32B–70B+Raisonnement avancé, proche du cloud sur beaucoup de tâches. Exige une vraie station GPU.

La quantization : la clé pour faire rentrer un modèle

Un modèle est entraîné en 16 bits (FP16). La quantization compresse les poids (8, 5, 4 bits…) pour diviser la mémoire requise, avec une perte de qualité maîtrisée. GGUF est le format de fichier standard côté llama.cpp/Ollama/LM Studio.

NiveauBits/poidsMémoire vs FP16QualitéQuand l'utiliser
Q8~8 bits~50 %Quasi intacteSi vous avez la mémoire, qualité max
Q6_K~6 bits~40 %ExcellenteTrès bon compromis
Q5_K_M~5 bits~35 %Très bonneCompromis recommandé
Q4_K_M~4 bits~30 %BonneLe défaut le plus courant — meilleur rapport taille/qualité
Q3 / Q22–3 bits~20–25 %DégradéeUniquement pour faire tenir un gros modèle de force
Règle d'orPrivilégiez un modèle plus gros mais plus quantizé plutôt qu'un petit modèle en haute précision. Un 14B en Q4 bat presque toujours un 7B en Q8 à mémoire égale.

Combien de mémoire pour quel modèle ?

Estimation pratique : mémoire ≈ (nb paramètres en milliards) × (bits/8) + ~15–25 % d'overhead (cache KV pour le contexte, activations). En Q4, comptez grossièrement ~0,6 Go par milliard de paramètres.

Ajoutez de la marge pour le contexte long : le cache KV peut consommer plusieurs Go à 32k+ tokens. Si ça déborde, la couche manquante est offloadée en RAM/CPU → ça marche mais ça ralentit fortement.

GPU vs CPU vs Apple Silicon

🎮 GPU (VRAM)

Le roi de la vitesse. Tout le modèle doit tenir en VRAM pour être rapide. NVIDIA (CUDA) est le standard. C'est la VRAM, pas la puissance brute, qui détermine quel modèle vous pouvez charger.

🖥️ CPU (RAM)

Fonctionne avec beaucoup de RAM système (moins chère), mais nettement plus lent (bande passante mémoire limitée). OK pour des petits modèles ou du batch non interactif, pénible en chat temps réel sur gros modèle.

🍎 Apple Silicon

La mémoire unifiée (M1–M4) est partagée CPU/GPU : un Mac 64 Go peut charger un 70B, ce qu'aucun laptop PC ne fait. Excellent rapport perf/watt. ~75 % de la RAM est allouable au GPU.

5Lire des PDF & interroger ses docs : le RAG 100 % local

Un LLM seul ne connaît pas vos documents. Le RAG (Retrieval-Augmented Generation) retrouve les passages pertinents dans vos fichiers et les injecte dans le prompt. Tout — modèle, embeddings, base vectorielle — peut rester sur votre machine : aucune donnée ne sort.

Le principe en 4 étapes

Ingestion

On charge les sources (PDF, Word, Markdown, code…) et on en extrait le texte brut. Un PDF scanné passe par de l'OCR (Tesseract) au préalable.

Chunking

On découpe le texte en morceaux (~300–800 tokens, avec chevauchement). Trop gros = bruit ; trop petit = perte de contexte. C'est l'étape qui fait le plus la qualité du RAG.

Embeddings

Chaque chunk est transformé en vecteur par un modèle d'embeddings local (ex. nomic-embed-text, bge-m3, all-MiniLM) puis stocké dans une base vectorielle.

Retrieval + génération

La question est elle aussi vectorisée ; on récupère les chunks les plus proches (similarité cosinus), on les colle dans le prompt, et le LLM répond en citant vos sources.

Les briques concrètes

CoucheOptions localesNotes
Embeddings locauxnomic-embed-text, bge-m3, mxbai-embed-large, all-MiniLMServis par Ollama/LM Studio. bge-m3 gère bien le multilingue (FR).
Base vectorielleChroma Qdrant FAISSFAISS = librairie en mémoire (simple, rapide). Chroma = facile, fichier local. Qdrant = robuste, scalable, type serveur.
Orchestration (code)LlamaIndex, LangChainPour construire un pipeline sur mesure (Python). LlamaIndex est très orienté RAG.
Clé en main (no/low-code)AnythingLLM, Open WebUI, LM Studio, GPT4AllGlisser-déposer des docs, base vectorielle gérée pour vous.

Trois façons de le mettre en place

① Le plus simple

LM Studio (« Chat with Documents ») ou GPT4All : on dépose un PDF et on pose des questions. Zéro config, idéal pour tester.

② Le bon compromis

AnythingLLM ou Open WebUI branché sur Ollama : espaces de travail, gestion de corpus, base vectorielle (Chroma/Qdrant) intégrée, multi-utilisateurs. Le choix d'équipe.

③ Sur mesure (dev)

LlamaIndex/LangChain + Qdrant + Ollama : pipeline maîtrisé, intégrable dans une app C#/Python, contrôle total du chunking et du retrieval.

Stack 100 % local typiqueOllama (LLM + embeddings) + Qdrant ou Chroma (vecteurs) + AnythingLLM ou LlamaIndex (orchestration). Tout tourne sur la même machine, rien ne sort du réseau.

★Recommandations de setup

👤 Dev solo

Objectif : assistant code/texte privé + RAG sur ses propres docs.

  • Machine : laptop GPU 8–12 Go VRAM, ou Mac (Apple Silicon) 16–32 Go.
  • Runtime : Ollama (intégration éditeur/CLI) ou LM Studio si vous préférez le GUI.
  • Modèles : un 7B–14B en Q4 généraliste + qwen2.5-coder:7b pour le code.
  • RAG : LM Studio « Chat with Documents » ou AnythingLLM + nomic-embed-text.

👥 Petite équipe

Objectif : service partagé, confidentiel, sur le corpus de l'entreprise.

  • Machine : station serveur GPU 24 Go (RTX 4090/A-series) ou Mac Studio 64–128 Go.
  • Runtime : Ollama (ou vLLM si fort débit) derrière l'API OpenAI locale.
  • Modèles : 32B en Q4 par défaut, 70B si la machine suit.
  • Front + RAG : Open WebUI ou AnythingLLM (multi-utilisateurs) + Qdrant + bge-m3.
  • Bonus : garder une porte cloud pour les tâches les plus dures (hybride).
À retenirCommencez petit (Ollama + un 7B + un PDF en RAG), mesurez vos vrais besoins en tokens/s et en qualité, puis investissez dans le matériel. La VRAM est la ressource qui décide de tout.
