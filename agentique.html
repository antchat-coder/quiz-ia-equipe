L'agentique : faire travailler des agents,
et faire travailler les humains avec eux

Passer d'un agent isolé à plusieurs agents qui collaborent, sans se noyer. La vraie question : comment chaque salarié apprivoise l'IA sans se faire remplacer, et pourquoi cet enjeu dépasse largement le code.

§Lexique

Les mots-clés de la page, en une ligne. À garder ouvert à côté.

TermeDéfinition
AgentUn LLM à qui on donne des outils (lire/écrire des fichiers, lancer des commandes) et qui agit en boucle jusqu'à un résultat, au lieu de juste répondre.
OrchestrationLa façon d'enchaîner et de coordonner un ou plusieurs agents : qui fait quoi, dans quel ordre, avec quelles limites, et comment on récupère les résultats.
Sub-agentUn agent lancé par un autre agent pour une sous-tâche délimitée (recherche, revue…), avec son propre contexte, qui rend son résultat à l'agent principal.
WorktreeUne copie de travail Git supplémentaire du même dépôt, sur une branche isolée. Permet à plusieurs agents de bosser en parallèle sans se marcher dessus.
Vibe codingProduire un logiciel en décrivant l'intention en langage naturel et en laissant l'IA écrire le code — sans forcément écrire une ligne soi-même.
TDDTest-Driven Development — écrire le test avant le code. Donne à l'agent un critère objectif de réussite (le test passe ou non).
MCPModel Context Protocol : un standard pour brancher un agent sur des outils externes (GitHub, base de données, monitoring…).
HarnaisLe cadre de contrôle autour des agents : branches dédiées, tests obligatoires, pas de commit auto, relecture humaine. Il empêche l'« IA en roue libre ».
Augmenter vs remplacerDeux visées opposées de l'IA au travail : augmenter = rendre l'humain meilleur/plus rapide ; remplacer = faire à sa place. Le même outil peut servir les deux.

1Commencer petit : 3 ou 4 agents maximum

La tentation, quand on découvre le multi-agent, c'est d'en lancer dix. Erreur. Chaque agent supplémentaire ajoute du coût, du contexte à suivre et des points de collision. Au-delà de 3-4 agents actifs en parallèle, un humain seul ne peut plus vraiment savoir ce qui se passe — et l'intérêt s'effondre.

Pourquoi se limiter

  • Charge cognitive. Vous restez le relecteur. 4 diffs à valider, c'est gérable ; 10, non.
  • Coût. Chaque agent consomme des tokens en continu. Le parallélisme se paie.
  • Collisions. Plusieurs agents sur les mêmes fichiers = conflits, écrasements, travail perdu.

La bonne maille de départ

  • 1 agent principal qui pilote et à qui vous parlez.
  • 2-3 sub-agents spécialisés et bornés (explorer, coder, relire).
  • Des tâches indépendantes : chacun sur son périmètre, idéalement son worktree.
Règle pratique Monter en nombre d'agents seulement quand vous avez rendu leur travail observable et isolé. Le nombre d'agents que vous pouvez piloter = le nombre de résultats que vous pouvez réellement relire et arbitrer.

2Utiliser les GitHub / Git worktrees

Le mécanisme concret qui rend le parallélisme sain. Un worktree Git, c'est une seconde (troisième…) copie de travail du même dépôt, rattachée à une branche différente. Chaque agent travaille dans son worktree, sur sa branche, sans jamais toucher au dossier des autres.

Le problème qu'ils résolvent

Sans worktree, deux agents dans le même dossier éditent les mêmes fichiers en même temps : l'un écrase l'autre, les tests d'un agent tournent sur le code de l'autre, le diff devient illisible. Avec worktrees, chacun a un bac à sable réel — même historique Git, dossiers séparés.

# Un worktree par tâche/agent, chacun sur sa branche
git worktree add ../recall-feat-429   feat/limite-429
git worktree add ../recall-migration  refactor/rxjs-signals
git worktree add ../recall-tests      test/upsert-unicite

# chaque agent est lancé à la racine de SON worktree
cd ../recall-feat-429 && claude

Ce que ça débloque

  • Vrai parallélisme : 3 agents, 3 branches, zéro collision.
  • Isolation des tests : chaque agent teste son code.
  • Une PR propre par worktree, relue indépendamment.
  • Rollback trivial : on jette le worktree, le dépôt reste intact.

Le harnais qui va avec

  • Une branche dédiée par worktree, jamais main.
  • Tests obligatoires avant toute proposition de merge.
  • Vous relisez et fusionnez les branches une par une.
  • Nettoyage : git worktree remove quand c'est fusionné.

Certaines interfaces d'agents créent et nettoient le worktree automatiquement (mode « isolation worktree »). Le principe reste le même : un espace de travail Git isolé par agent.

Le merge reste une décision humaine Les agents produisent des branches ; ils ne décident pas de les fusionner. La décision de merger — accepter ce travail dans la base commune — revient à l'humain. Ce n'est pas une formalité : c'est le moment où l'on exerce son jugement — relire le diff, arbitrer entre deux branches concurrentes, refuser ce qui ne tient pas. Les worktrees isolent l'exécution justement pour laisser ce point de contrôle intact. L'agent accélère ; la décision et la responsabilité restent nôtres.

3Aider chaque salarié à apprivoiser l'IA

Le sujet technique masque le vrai sujet : les gens. Un déploiement d'IA échoue rarement pour des raisons de modèle ; il échoue parce que les salariés y voient une menace, ou ne savent pas quoi en faire.

La problématique : remplacer ou augmenter ?

Remplacer — « l'IA fait à ta place »

L'IA prend la tâche. Le salarié la subit, la surveille, ou la perd. Vécu comme une menace, ça déclenche résistance, désengagement, contournement. Et ça se retourne : on perd le savoir-faire qu'on croyait « automatiser ».

Augmenter — « l'IA améliore ton travail »

L'IA enlève le répétitif et rend le salarié plus rapide, plus précis, capable de choses qu'il ne faisait pas seul. Le jugement, la décision, la responsabilité restent à lui. Vécu comme un levier, pas comme un remplaçant.

Le même outil peut servir les deux visées. Ce qui fait la différence, c'est l'intention du déploiement et la place laissée à l'humain. Le rôle du management n'est pas de choisir un outil, mais de choisir de quel côté on le met.

L'idée directrice : avancer ensemble, en donnant des responsabilités Plutôt que « l'IA remplace des tâches », proposer : « chacun avance avec l'IA et gagne en responsabilité ». Le salarié qui délègue le répétitif à l'IA récupère du temps et du périmètre pour des décisions à plus forte valeur. On ne réduit pas le poste, on le fait monter d'un cran. C'est un contrat clair : l'IA prend le mécanique, l'humain prend la responsabilité.

En pratique, pour accompagner

  • Commencer par des cas sans enjeu (compréhension, brouillon, recherche) pour créer la confiance.
  • Nommer explicitement ce que l'IA ne fait pas : décider, valider, assumer.
  • Donner à chacun un vrai périmètre de responsabilité au-dessus de l'IA, pas à côté.
  • Valoriser ceux qui apprennent à bien s'en servir, sans stigmatiser ceux qui débutent.

4L'IA brouille les frontières entre les postes

Un effet moins discuté, mais profond : l'IA redistribue qui peut faire quoi. Les cloisons entre « celui qui code » et « celui qui ne code pas » deviennent poreuses, dans les deux sens.

Le non-codeur qui livre du logiciel

Un profil métier, un designer, un chef de projet peut désormais « vibe coder » un site ou un outil interne sans écrire une ligne de code — en décrivant son intention à un agent. Des tâches qui exigeaient un développeur deviennent accessibles. La frontière « sait coder / ne sait pas coder » perd de sa netteté.

Ce qui compte n'est plus la syntaxe

Écrire du code n'est plus le goulot d'étranglement. Ce qui fait la différence, c'est de savoir quoi demander et comment juger le résultat — c'est-à-dire les fondamentaux d'ingénierie, pas la maîtrise d'un langage.

Le retournement Quelqu'un qui maîtrise le TDD (donner à l'IA des tests comme critère de réussite) peut faire produire à un agent un meilleur code que beaucoup de développeurs professionnels qui codent « au feeling ». De même, quelqu'un qui connaît les principes d'architecture et sait les énoncer à une IA obtient des résultats structurés, là où un codeur chevronné mais sans cadre obtiendra du code qui marche mais ne tient pas.

Autrement dit : la valeur se déplace de l'exécution (écrire les lignes) vers le cadrage et le jugement (quoi construire, quels tests, quelle architecture, quelle qualité on accepte). Ce sont des compétences transférables — ce qui explique pourquoi les frontières entre postes bougent autant.

5Eric Sadin — la critique à ne pas esquiver

Impossible de parler sérieusement d'IA au travail sans écouter ses critiques les plus tranchants. Éric Sadin, philosophe et essayiste français, est l'une des voix les plus radicales sur le sujet. On peut ne pas partager ses conclusions ; les ignorer serait naïf.

Sa pensée, en résumé

  • Un « antihumanisme radical ». Pour Sadin, l'IA n'est pas un simple outil : c'est une technologie qui prétend dire le vrai et dicter la conduite à notre place — elle « suggère », « recommande », « décide », et nous déchargeons peu à peu notre jugement sur elle.
  • Des « technologies de l'injonction ». À force de nous dire quoi faire (quel trajet, quel achat, quelle formulation), ces systèmes érodent notre autonomie de décision et notre rapport singulier au monde.
  • Le « désert de nous-mêmes ». En déléguant à la machine l'écriture, la création, la pensée, nous risquons de vider notre vie intérieure — la capacité même de nous éprouver comme êtres pensants et créateurs. C'est le cœur de son livre de 2025.
  • Une critique politique et économique. Il vise le « technolibéralisme » : une industrie qui marchandise nos comportements et impose son tempo à la société, sans débat démocratique réel.
« L'enjeu n'est pas seulement ce que l'IA fait, mais ce qu'elle nous fait devenir — et ce qu'elle nous retire de la faculté de penser et d'agir par nous-mêmes. »
— synthèse de la position de Sadin (paraphrase)

6Réflexion stratégique — toujours un coup d'avance

Au-delà de la critique, savoir anticiper : où va l'IA, quels coups jouer, et comment garder l'initiative plutôt que de subir. L'idée directrice — toujours avoir un coup d'avance.

🎯 « Le SamourAI | IA & Stratégie »

Une chaîne francophone qui analyse l'IA non pas comme une liste de gadgets, mais comme un système stratégique : les dynamiques invisibles (puissance de calcul, finance, géopolitique, marché du travail) qui déterminent qui gagne et qui perd. Anti-sensationnalisme, posture d'analyste plutôt que de chroniqueur de nouveautés — devise : « L'IA, enfin claire. Votre coup d'avance. » Elle ne commente pas le gadget de la semaine, mais le système qui le produit.

4 axes de contenu

  • Stratégie — qui détient la puissance de calcul et les modèles, positionnement concurrentiel.
  • Carrière / travail — comment les emplois se redéfinissent et comment s'adapter structurellement.
  • Finance — investissement, « suivre l'argent », géopolitique.
  • Technologie — architecture, outils, méthodes d'implémentation et d'intégration.

Pour qui : décideurs, stratèges, ingénieurs et professionnels qui raisonnent en années, pas en semaines. Ce que ce n'est pas : ni tutoriels, ni news de modèles — de la profondeur analytique plutôt que de la hype, pour anticiper carrière, investissements et décisions d'entreprise.

Le type d'angles

Plutôt que le modèle du jour, il déplace le regard : en stratégie, « vendre les pioches (Nvidia) rapporte plus que chercher l'or », ou pourquoi les géants acceptent de perdre de l'argent aujourd'hui. Côté carrière, « ce n'est pas l'IA qui prend ton job, c'est le collègue qui sait l'utiliser ». En finance & géopolitique, « suivre l'argent » et les vrais goulots — puce, énergie, data. Et sur la techno, pourquoi les entreprises échouent à déployer l'IA pour des raisons non techniques, ou si les agents sont une mode ou une vraie rupture.

Le fil rouge : la question que la plupart évitent — « ok, l'IA avance… mais concrètement, qu'est-ce que j'en fais » pour ma carrière, mes investissements, mes décisions.

7Former les juniors quand l'IA fait leur travail

Un angle mort dangereux. Le travail des juniors — le répétitif, le boilerplate, les tâches simples — est précisément ce que l'IA absorbe le mieux. D'où une question qui n'a rien de théorique.

Le paradoxe de la relève Si l'IA fait le travail des juniors, par où passe-t-on pour devenir senior ? Un senior s'est formé en faisant le travail simple, en se trompant, en lisant beaucoup de code. Supprimez cette marche, et vous cassez l'escalier : plus de juniors formés aujourd'hui = plus de seniors demain pour relire, arbitrer, et rattraper les erreurs de l'IA. À terme, plus personne d'humain avec le recul suffisant derrière la machine.

L'enjeu, posé nettement

  • Le savoir-faire se construit par la pratique, pas par la supervision d'une machine.
  • Un junior qui ne fait que valider ce que l'IA produit n'apprend pas à juger — il apprend à faire confiance.
  • Sans nouveaux seniors, la couche humaine de contrôle au-dessus de l'IA s'amincit, alors qu'elle devient plus critique.
  • C'est un risque collectif et différé : invisible à court terme, structurel à 5-10 ans.

Pistes

  • Faire des juniors ceux qui pilotent et critiquent l'IA tôt — mais sur des bases qu'ils ont vraiment comprises (leur faire faire, puis comparer avec l'IA).
  • Préserver des espaces d'apprentissage « à la main », même moins efficaces, comme un investissement de formation assumé.
  • Muscler ce qui ne s'automatise pas : lecture critique, architecture, tests, débogage de ce que l'IA a raté.

8Un enjeu de société — et la responsabilité des devs

Tout ce qui précède déborde très largement le développement logiciel. Le déplacement du travail, de la formation, du jugement, touche la société entière. Et les développeurs y ont une responsabilité particulière : ce sont eux qui choisissent, construisent et déploient ces systèmes.

Pourquoi l'IA locale apparaît comme une réponse

💶 Plus soutenable économiquement

Les coûts des modèles « frontières » (les plus gros, propriétaires) explosent : entraînement, inférence, dépendance à quelques fournisseurs. Une IA locale, tournant sur son propre matériel, transforme une rente à l'usage en investissement amorti — et sort de la spirale de coûts incontrôlés.

🗳️ Plus démocratique

Une IA locale ne dépend pas d'un acteur unique qui fixe les prix, les règles et ce qui est permis. Elle garde la donnée chez soi, rend l'accès indépendant du bon vouloir d'une plateforme, et redonne du contrôle aux organisations et aux personnes. Une réponse concrète à la critique de Sadin sur le technolibéralisme.

La responsabilité côté dev Choisir une IA locale, ouverte, contrôlable, n'est pas qu'une décision technique de coût ou de confidentialité — c'est un choix de société : moins de dépendance, plus de souveraineté, une empreinte et une gouvernance qu'on peut assumer. Les développeurs ne sont pas neutres dans ce choix. Voir le guide IA locale & RAG on-premise.

9La différence énorme entre les outils

« Utiliser l'IA pour coder » ne veut rien dire tant qu'on n'a pas précisé quel outil. L'écart entre eux est colossal : ce ne sont pas des variantes d'un même produit, mais des catégories différentes, avec des puissances et des philosophies opposées.

OutilNatureCe qu'il fait vraiment
Copilot 365 Assistant intégré Un assistant greffé dans la suite bureautique (Word, Excel, Outlook, Teams). Il aide à produire des documents et des mails, résume, reformule. Précieux pour le travail de bureau — mais ce n'est pas un agent qui code et exécute dans un dépôt.
GitHub Copilot Autocomplétion / chat De l'autocomplétion de code dans l'éditeur + un chat. Il suggère la ligne ou le bloc suivant, répond à des questions. Très efficace pour accélérer la frappe, mais reste centré sur « t'aider pendant que toi tu codes ».
Cursor Éditeur IA Un éditeur (fork de VS Code) pensé autour de l'IA : édition multi-fichiers, compréhension du projet, mode agent intégré. Plus proche de l'agentique que Copilot, tout en restant dans un environnement d'édition.
Claude Code Agent Un agent qui vit là où tu codes (terminal, IDE) : il lit le dépôt, modifie les fichiers, lance les commandes et boucle jusqu'au résultat. On ne l'assiste pas, on lui délègue une tâche et on relit le diff. C'est un changement de nature, pas de degré.
Le point à faire passer Mettre « Copilot » et « Claude Code » dans la même phrase induit en erreur. L'un suggère pendant que tu écris ; l'autre fait et vérifie tout seul pendant que tu arbitres. Choisir son outil, c'est choisir son mode de travail — assistant, éditeur augmenté, ou vraie délégation agentique.

10Créer des outils pour l'IA vs rafistoler de vieux logiciels

Dernière distinction, souvent invisible et pourtant déterminante. Quand on « branche un agent sur nos outils », il y a deux mondes très différents.

Concevoir des outils pour l'IA

Des interfaces pensées dès le départ pour être appelées par un agent : contrats clairs, entrées/sorties structurées, erreurs explicites, opérations sûres et idempotentes. C'est l'esprit de MCP : exposer des capacités faites pour être orchestrées. L'agent est fiable parce que l'outil est fait pour lui.

  • Actions atomiques, descriptibles en une phrase.
  • Sorties structurées, prévisibles, versionnées.
  • Erreurs lisibles par le modèle, garde-fous intégrés.

Rafistoler un vieux logiciel

Faire piloter par un agent une vieille application jamais prévue pour ça : cliquer dans une UI legacy, parser des sorties non structurées, contourner l'absence d'API. Ça peut marcher, mais c'est fragile, lent, et ça casse au moindre changement d'écran. On plaque de l'agentique sur un socle qui la refuse.

  • Interfaces instables, comportements implicites.
  • Aucune garantie, aucune reprise propre sur erreur.
  • Maintenance coûteuse à chaque évolution du legacy.
La conséquence stratégique La vraie valeur ne vient pas de « brancher l'IA sur l'existant » à tout prix, mais de concevoir des capacités faites pour être orchestrées. Les organisations qui repensent leurs outils pour l'IA obtiendront des agents fiables ; celles qui se contentent de rafistoler auront des démos qui impressionnent et des systèmes qui cassent. C'est très différent — et ça se décide en amont.
