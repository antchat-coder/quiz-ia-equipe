Temps 1 / 4

L'agentique

« Ce n'est plus un chatbot, c'est un collègue qui agit »

Le problème

Vécu

Le chatbot te donne du code. À toi de le coller, l'adapter, lancer les tests, voir l'erreur, retourner copier l'erreur dans le chat, recoller… 6 allers-retours pour un test qui passe. Le chatbot ne voit ni ton repo, ni ta sortie de test.

La différence de fond

LLM / chatbotAgent
Produit du texteProduit des actions sur ton repo
Ne voit que ce que tu collesLit les fichiers, lance les commandes, lit la sortie
Un coup, puis stopBoucle jusqu'au résultat

La boucle agentique

Lire
l'arborescence, le code
→
Planifier
propose un plan
→
Exécuter
édite, lance tests & commandes
→
Observer
lit la sortie / l'erreur
→
Corriger
… et reboucle

La clé, c'est Observer : l'agent voit le résultat réel de ses actions. C'est ce qu'un chatbot ne peut pas faire.

Orchestration IA : le cerveau de la boucle

Un agent utile n'est pas juste « automatique ». Il prend des décisions en continu.

Prioriser
quel fichier lire en premier
→
Limiter
combien de tentatives avant escalade
→
Arbitrer
corriger le code ou clarifier la demande
  • Signal vert : les tests passent en 1 à 3 boucles
  • Signal orange : l'agent touche des fichiers hors scope
  • Signal rouge : plus de 3 boucles sans progrès → on reformule

L'orchestration sert à garder l'agent efficace et prévisible, pas « autonome coûte que coûte ».

Exemple agentique simple · ajouter des tests xUnit

Tâche donnée à l'agent (bug réel : codes d'identification en doublon) :

« Ajoute les tests xUnit sur l'upsert d'un code d'identification :
cas nominal (200), code en doublon rejeté, code vide (400).
Fais-les passer. »

Ce qu'il déroule, seul

  • Lit recall-identification-code-management.service.ts (contrat upsert) + le handler/controller côté API
  • Planifie : 3 cas manquants, repère qu'il faut mocker IMediator (dispatch CQRS)
  • Écrit les tests (Arrange/Act/Assert, Theory/Fact)
  • Lance dotnet test → lit la sortie
  • 1 rouge : le doublon n'est pas rejeté (aucun contrôle d'unicité) → révèle le vrai bug

Ce que ça t'enlève : le boilerplate de test et les aller-retours d'erreurs. Ce que ça ne t'enlève pas : décider si les cas testés sont les bons. Ici le test rouge pointe direct l'origine du crash d'import. Tu relis le diff.

Temps 3 / 4

Les Skills

Apprendre nos conventions une fois pour toutes

Le problème

Vécu

À chaque session tu réexpliques : « nos commits suivent Conventional Commits », « nos revues vérifient X, Y, Z », « notre checklist de release c'est… ». Ou alors tu mets tout dans un gros fichier de règles que l'agent traîne en permanence → coût en tokens, bruit.

Skill = un savoir-faire chargé à la demande

Un dossier avec un fichier SKILL.md : un frontmatter YAML (name + description), puis des instructions en markdown. L'agent ne charge le contenu que si la description correspond à la tâche → chargement progressif, coût quasi nul le reste du temps.

CLAUDE.md vs Skill — ne pas confondre

CLAUDE.md

Toujours chargé. Les règles non négociables du repo.

# CLAUDE.md
- Ne jamais committer de .env
- Tests obligatoires avant tout commit
- Réponses en français

Skill

Chargé à la demande. Un savoir-faire précis, quand c'est pertinent.

# .claude/skills/code-review/
Comment on écrit une revue
de code ici — chargé seulement
quand on demande une revue.

Règle simple : toujours vrai → CLAUDE.md. Vrai pour une tâche précise → Skill.

Un Skill réaliste · convention de commit

# .claude/skills/git-commit/SKILL.md
---
name: git-commit
description: Rédige les messages de commit de l'équipe.
  À utiliser dès qu'on prépare ou écrit un commit.
---

# Convention de commit
- Format Conventional Commits : type(scope): sujet
- Types : feat, fix, refactor, test, chore, docs
- Sujet à l'impératif, < 72 caractères, en français
- Corps : le pourquoi, pas le quoi
- Référencer le ticket : Refs #1234

## Exemple
feat(deposit): affiche un message clair sur refus 429

Gère la limite de dépôts atteinte dans onBeforeUpload
au lieu de simplement journaliser l'erreur. Refs #482

Pourquoi c'est puissant en équipe

  • Un Skill projet vit dans .claude/skills/ → il se versionne dans git
  • Tu l'écris une fois, toute l'équipe (et l'agent de chacun) l'a au prochain pull
  • Le savoir tacite (« comment on fait ici ») devient explicite et révisable en PR
  • Idées immédiates : checklist de releasestyle de revue C#format de commitconventions Angular
Le déclic

L'onboarding d'un nouveau passe en partie de « lis ce wiki de 40 pages » à « l'agent connaît déjà nos conventions, parce qu'elles sont dans le repo ».

Temps 4 / 4

MCP

Model Context Protocol — brancher l'agent sur nos outils

Le problème

Vécu

L'agent sait coder, mais il est isolé. Le ticket est dans GitHub/Jira, l'erreur dans le monitoring, le board ailleurs. Toi tu fais la navette : lire le ticket, recopier le contexte, ouvrir la PR à la main, mettre le board à jour.

Skill vs MCP — la distinction nette

SkillServeur MCP
Dit COMMENT se comporterDonne de NOUVELLES capacités
Des instructions (markdown)Des outils / connexions externes
« écris le commit comme ça »« lis l'issue, ouvre la PR »

Ce que MCP débloque pour ce public

Pour les devs

  • Lire / créer des issues GitHub
  • Ouvrir une PR dans la foulée
  • Interroger une base de données
  • Remonter les erreurs depuis le monitoring (Sentry…)

Pour le chef de projet

  • Synchroniser un board (Jira / Linear)
  • Générer un point d'avancement depuis les tickets
  • Lier PR ↔ ticket automatiquement

Un serveur MCP s'ajoute une fois (config projet), puis l'agent l'utilise comme des outils natifs.

Le déclic · du ticket à la PR, d'un trait

> Prends l'issue #482, implémente-la, et ouvre une PR.
Lit l'issue #482 (MCP GitHub)
→
Écrit le code (Claude Code)
→
Lance les tests (dotnet/ng)
→
Ouvre la PR liée (MCP GitHub)

Orchestration en action

L'agent enchaîne les outils dans un ordre précis : lire l'issue, coder, tester, ouvrir la PR. Le harnais fixe les limites, toi tu valides le résultat.

Note

Agentique + Claude Code + Skill (le commit/PR au format équipe) + MCP (GitHub) : les 4 temps s'assemblent ici. Tu restes le relecteur de la PR.

Limites et harnais : garder le contrôle

Le harnais en 3 étapes

  • Pré-vol : l'agent annonce les fichiers qu'il compte modifier
  • Exécution : branche dédiée, tests obligatoires, pas de commit automatique
  • Post-vol : résumé du diff + statut clair des tests

Signaux à surveiller

  • Vert : scope respecté, tests en hausse
  • Orange : fichiers inattendus, boucles longues
  • Rouge : modifications de tests pour masquer le bug

Ce cadre évite le mode « IA en roue libre ». L'agent accélère, l'humain décide.

Objections fréquentes / réponses

ObjectionRéponse nuancée
« Et la sécurité de notre code ? » À cadrer : périmètre d'accès au repo, ce qui sort ou non, paramètres réseau/entreprise. À valider avec qui gère ces réglages avant un usage large.
« C'est fiable ? » Pas infaillible. Mais la boucle tests rattrape beaucoup : il voit le rouge et corrige. Fiabilité = bon cadrage + relecture, pas confiance aveugle.
« Ça remplace les devs ? » Non. Ça enlève le répétitif (boilerplate, migrations mécaniques, tests manquants). Le jugement — quoi construire, quels cas tester, quelles décisions d'archi — reste à nous.
